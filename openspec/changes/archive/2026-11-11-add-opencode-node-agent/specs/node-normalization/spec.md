## Purpose

Нормализация узла выполняется выбранным агентом узла: Cursor по умолчанию или OpenCode v2.

## MODIFIED Requirements

### Requirement: Сбор логов операции нормализации

Система SHALL собирать лог выполнения операции нормализации узла из `stdout` и `stderr` процесса выбранного агента узла, а также добавлять системные события стадии операции (`normalize`, `sync`, `done/error`). Для OpenCode система MUST разбирать JSONL (`--format json`) и MUST завершать операцию ошибкой, если в потоке есть событие `error`, даже при нулевом коде выхода процесса. Каждая запись MUST иметь монотонный offset, временную метку и тип потока.

#### Сценарий: Логи stdout/stderr во время normalizing

- **WHEN** операция нормализации запущена
- **THEN** записи вывода агента добавляются в лог операции с типом `stdout` или `stderr`

#### Сценарий: Системные записи стадий

- **WHEN** операция переходит между стадиями
- **THEN** в лог добавляется запись типа `system` с описанием перехода

#### Сценарий: Ошибка в JSONL OpenCode

- **WHEN** выбран агент `opencode` и в stdout есть JSONL-событие `type=error`
- **THEN** операция нормализации завершается ошибкой и MUST NOT считаться успешной только из-за нулевого кода выхода

### Requirement: Автоматический sync после успешной нормализации

После завершения шага нормализации со статусом success система SHALL автоматически выполнять `sync` и MUST отражать итог обоих шагов в результате операции.

#### Сценарий: Нормализация и sync успешны

- **WHEN** агент завершил нормализацию успешно и `sync` выполнился без ошибок
- **THEN** итоговый статус операции success, а изменения узла доступны в обычном git-first потоке

#### Сценарий: Нормализация успешна, sync завершился ошибкой

- **WHEN** нормализация завершилась success, но `sync` вернул ошибку
- **THEN** операция возвращает ошибку шага sync с диагностикой, при этом факт успешной локальной нормализации сохраняется

## ADDED Requirements

### Requirement: Нормализация узла через настроенного агента

Система SHALL предоставлять серверный сценарий нормализации конкретного узла базы знаний через настроенного агента узла (`cursor` или `opencode`) с промтом, сформированным на основе текущего содержимого узла и его метаданных. Операция MUST быть привязана к одному path узла и MUST возвращать диагностируемый статус выполнения. Агент MUST запускаться с рабочим каталогом, равным корню базы (`KB_DATA_PATH`).

#### Сценарий: Успешный запуск нормализации

- **WHEN** клиент запрашивает нормализацию существующего узла и выбранный агент доступен
- **THEN** сервер запускает задачу нормализации для этого path и возвращает идентификатор операции со статусом running

#### Сценарий: Узел не найден

- **WHEN** клиент запрашивает нормализацию для несуществующего path
- **THEN** сервер возвращает ошибку not found и MUST NOT запускать агента

### Requirement: Выбор агента узла

Система SHALL выбирать агента для нормализации и agent-edit одной настройкой `KB_NODE_AGENT`. Пустое значение и `cursor` MUST означать Cursor Agent. Значение `opencode` MUST означать OpenCode v2. Любое другое значение MUST останавливать старт `kb serve`. Отсутствие бинаря выбранного агента в PATH MUST давать ошибку runtime на старте джобы (503) и MUST NOT создавать операцию. Сервер MUST оставаться доступен для чтения базы, если бинарь отсутствует.

#### Scenario: Значение по умолчанию

- **WHEN** `KB_NODE_AGENT` не задан
- **THEN** нормализация использует `cursor-agent`

#### Scenario: Неизвестное значение

- **WHEN** `KB_NODE_AGENT` задан значением, отличным от `cursor` и `opencode`
- **THEN** `kb serve` завершается ошибкой конфигурации и HTTP-сервер не стартует

#### Scenario: OpenCode не установлен

- **WHEN** `KB_NODE_AGENT=opencode` и `opencode` отсутствует в PATH
- **THEN** старт нормализации возвращает 503, операция не создаётся, чтение базы остаётся доступным

### Requirement: Конфигурация OpenCode для джоб узла

При `KB_NODE_AGENT=opencode` система SHALL требовать `KB_NODE_AGENT_MODEL` на старте `kb serve`. Модель каталога OpenCode Go MUST задаваться как `opencode-go/<id>`, а ключ подписки MUST читаться из `OPENCODE_API_KEY` окружения процесса. Для модели `opencode-go/*` система MUST NOT подменять endpoint каталога Go своим `baseURL`. Свой OpenAI-совместимый endpoint SHALL задаваться парой `KB_NODE_AGENT_API_URL` и `KB_NODE_AGENT_API_KEY` и MUST NOT сочетаться с моделью `opencode-go/*`. Состояние и сгенерированный конфиг OpenCode MUST храниться вне репозитория базы. Процесс OpenCode MUST получать запрет shell, сетевых инструментов, subagent, question и записи вне файла текущего узла.

#### Scenario: OpenCode Go

- **WHEN** `KB_NODE_AGENT=opencode`, `KB_NODE_AGENT_MODEL=opencode-go/kimi-k3` и задан `OPENCODE_API_KEY`
- **THEN** джоба запускает OpenCode с этой моделью и ключом из окружения, без собственного `baseURL` для провайдера `opencode-go`

#### Scenario: Go без ключа

- **WHEN** `KB_NODE_AGENT=opencode`, модель начинается с `opencode-go/` и `OPENCODE_API_KEY` пуст
- **THEN** `kb serve` завершается ошибкой конфигурации

#### Scenario: OpenCode без модели

- **WHEN** `KB_NODE_AGENT=opencode` и `KB_NODE_AGENT_MODEL` пуст
- **THEN** `kb serve` завершается ошибкой конфигурации

#### Scenario: Свой endpoint вместе с Go

- **WHEN** модель начинается с `opencode-go/` и задан `KB_NODE_AGENT_API_URL`
- **THEN** `kb serve` завершается ошибкой конфигурации

#### Scenario: Состояние вне базы

- **WHEN** выполняется джоба OpenCode
- **THEN** kb не создаёт `opencode.json` и каталоги состояния OpenCode внутри `KB_DATA_PATH`

## REMOVED Requirements

### Requirement: Нормализация узла через Cursor Agent

**Reason:** Нормализация больше не привязана только к Cursor. Поведение перенесено в требование «Нормализация узла через настроенного агента».

**Migration:** Установки без `KB_NODE_AGENT` по-прежнему используют Cursor. Менять клиентов не нужно.
