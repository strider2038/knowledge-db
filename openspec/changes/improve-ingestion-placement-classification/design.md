## Context

Placement builder собирает карту тем, similar nodes и keywords до первого вызова LLM. Сейчас любая непустая тема получает бонус `theme_density`, а совпадение общего профиля источника даёт ещё один бонус. В результате темы без предметного совпадения попадают в shortlist. Дополнительно родительская тема накапливает доли score от нескольких similar nodes и может обогнать более точную дочернюю тему.

Изменение не затрагивает API, формат frontmatter или offline fallback.

## Goals / Non-Goals

**Goals:**

- Ранжировать темы по предметной близости, а не по размеру или форме источника.
- Не предлагать пустые родительские каталоги как конечную тему.
- Сохранить обзор разных веток базы в compact theme map.
- Уменьшить шум от длинного входа и подстрочных совпадений.

**Non-Goals:**

- Не добавлять embeddings или новую внешнюю зависимость.
- Не вводить ручной словарь предметных синонимов.
- Не менять само дерево тем или уже сохранённые узлы.
- Не гарантировать полностью детерминированный итог LLM при одинаковом shortlist.

## Decisions

### 1. Candidate theme требует предметного сигнала

`theme_density`, `source_kind` и `content_profile` удаляются из score. Кандидат попадает в shortlist только при совпадении path/keywords, сигнале similar node или явной инструкции пользователя. `NodeCount` остаётся диагностикой.

Альтернатива — снизить бонус плотности. Отклонена: даже малый бонус систематически решает неопределённость в пользу уже крупной темы.

### 2. Пустой parent не является placement candidate

Родитель получает ослабленный similar-node signal только если в нём есть узлы напрямую. Пустые navigation-only parents остаются в theme map, но не предлагаются как конечное место.

### 3. Theme map выбирается по веткам

При превышении лимита темы группируются по первому сегменту пути и выбираются round-robin. Внутри ветки приоритет имеют темы с большим числом прямых узлов, затем используется стабильная сортировка по пути; корневой каталог не получает отдельного бонуса. Это сохраняет обзор базы, не раздувая prompt.

### 4. Компактные токены и точное совпадение

Placement query не включает `source_kind`, `content_profile` и `type`. Из текста, URL и автора выбирается не более 24 терминов. Повторяющиеся термины приоритетнее, затем учитывается позиция первого появления и стабильная лексическая сортировка. Совпадение с path/title/keywords/annotation/body выполняется по целому токену, а не подстроке; для простого английского множественного числа используется нормализованная форма токена.

### 5. Prompt явно разделяет предмет и форму

Prompt требует выбирать самую узкую подходящую предметную тему. Он разрешает новую тему, если shortlist не подходит, но сначала требует уточняющий search. Примеры отделяют agentic coding от agent memory, RAG, MCP, LLM models и обычных online services.

## Risks / Trade-offs

- [Недостаточно сигналов в короткой заметке] → LLM видит balanced theme map и может вызвать `search_placement_candidates`.
- [Точное token matching хуже учитывает русскую морфологию] → similar-node index и LLM остаются основными semantic fallback; стеммер не добавляется.
- [Новая тема может создать дубль-синоним] → prompt требует сначала выполнить placement search и предпочесть существующий точный путь.

## Migration Plan

Миграция данных не требуется. Изменение применяется к новым ingestion-запросам. Откат — возврат к прежнему scoring и prompt.
